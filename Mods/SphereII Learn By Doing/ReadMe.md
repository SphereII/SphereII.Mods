
Version: TBD
- The skill progress bars now colour themselves from decay. SCore has computed a decay colour on all three skill row controllers for some time, but the bars were painted with a literal green and nothing ever read the {color} binding, so a skill drifting toward decay looked identical to one being used daily. All three BarContent sprites now bind it: green while the decay counter is at or below 2, yellow to 4, red beyond.
- That binding could not have worked as written. The colours were built with new Color(0, 255, 54, 128) - byte values passed to a constructor that takes floats 0-1 - and CachedStringFormatterXuiRgbaColor takes a Color32, so Unity's implicit conversion clamped every channel through Mathf.Clamp01 and delivered opaque cyan (0,255,255,255) instead of translucent green. The fallback path was worse: it assigned Color.ToString(), which is "RGBA(0.000, 255.000, ...)" and not a colour string XUi can parse at all. Both are fixed in SCore; the thresholds and the three colours now live in one place, Features/LearnByDoing/Scripts/LbdDecayColor.cs, rather than being restated in each of the three postfixes.
- Needs SCore 3.1.25.1014 or later for that. An older SCore leaves the bars cyan rather than green - wrong, but not broken.
- Added a Learn By Doing section to the 0-Help Screens window: Overview, Leveling, Decay and Changes. Wrapped in a conditional on mod_loaded('sphereii_help_screens'), so it is a no-op when that modlet is absent. Note mod_loaded takes the ModInfo Name value, not the folder or display name.
- Debug logging is now gated on $lbd_debug instead of HasBuff god. Turn it on in the console with setcvar $lbd_debug 1, off with setcvar $lbd_debug 0. All three were referenced but never defined, so NotHasBuff was always true and those perks scored on every hit taken with no throttle.

Spam crafting a stone axe on day 1 logged 27 Crafting Seeds - Applying Cooldown (Craft) lines. The two XP awards use a direct requirement and correctly stayed silent, which is what gave the bug away. - attStrength was the only progression whose debug lines carried no (+...) payload, so its XP could not be read off a log like every other one. Added $lbd_xp_melee_base, $lbd_xp_melee_power_base and $lbd_xp_strength_block_bonus to the three messages.
- Note on those last three: within an effect_group, triggered effects fire in document order, and every award that requires NotHasBuff on a cooldown is ordered ahead of the AddBuff that applies it - 188 such pairs, no exceptions. A throttle scoped more broadly than its award therefore costs at most one cooldown window; it can never block XP outright. 27 further requirement differences of this kind remain, 17 of them differing only by the self NotHasBuff and 8 more only by IsAlive, and are left alone deliberately.
- All 671 debug lines now use LogMessageCVars, SCore instead of vanilla LogMessage. Vanilla writes the message verbatim, so a line reading "(+@$lbd_xp_melee_base)" reached Player.log with the cvar name in it rather than its value - a debug line that could not answer the one question it exists for. The new action expands @cvar tokens against the player first, so the same message logs "(+1)". The token syntax is what the configs already wrote, so not one message had to change; only the action attribute did.
- A token naming a cvar the player does not have logs as <unset:name> rather than 0. The game reads an unset cvar as 0, which is exactly how four award paths in this mod paid nothing for so long without anyone noticing; the log now says so out loud.
- Rule #1: Cardio (Run) quoted the wrong cvar. Its message named $perkruleonecardio_lbd_xp, the running accumulator, rather than the $lbd_xp_attribute_synergy_base it actually awards, so once the values were being expanded the line read "Attempting XP Gain (+93)" and climbed. Checked all 185 token carrying lines against the value their award pays; this was the only mismatch.
- T0 starter gear now scores. Stone axes, wooden clubs, bone knives, the pipe weapons, primitive bow, stone spear, stone sledge, leather knuckles, pipe baton and stone shovel carry no UnlockedBy property, and every craft, scrap and repair award gates on ItemHasProperty UnlockedBy - so a new character's entire crafting output was invisible to the system across twelve skills. Added a T0 craft path and a T0 repair path to each, matched on two sibling requirements: ItemHasTags T0 and ItemHasTags <skill>Skill. No T0 item anywhere carries UnlockedBy, so these cannot double count with the existing paths.
- The T0 cap is 10, and it is not a preference. Vanilla unlocks the T1 recipes for all twelve of those skills at level 11 - iron tools, iron club, hunting knife and so on - so below 11 there is nothing else craftable. A T0 path that stops earlier strands the skill with no way to bridge to the next tier. LTE 10 pays right up to the point where T1 becomes craftable and the UnlockedBy paths take over.
- Raised the existing T0 repair caps on Clubs, Bows and Armor from 5 to 10, which stranded exactly that gap between 5 and 11. Harvesting Tools already used 10.
- Harvesting Tools' T0 repair matched on the harvestingSkill tag alone. That tag also sits on the eight iron and steel tools that do carry UnlockedBy, so repairing a looted iron pickaxe below level 11 paid twice, once through each path. All three existing T0 repair discriminators - harvestingSkill, RepairTools=resourceWood and ArmorGroup=groupPrimitive - are normalised onto the same T0 plus skill tag pair.
- T0 scrap is deliberately not included. Craft then scrap on a stone axe would loop for double XP with the materials mostly returned. Scrap stays T1 and above, where the items are expensive enough not to be worth farming.
- craftingTraps and craftingElectrician could not gain a single point. Every one of their recipes produces a block - dart trap, blade trap, turrets, generator bank, relays, switches, lights - and none of those has an entry in items.xml, which is where the awards were looking for UnlockedBy.

- Added RequirementCraftedBlockHasTags to SCore for that gap. It resolves the crafted ItemValue back to its block and tests the block's own tags, and both skills now score on craft and scrap through it.
- No blocks.xml patch is needed, and tag coverage was already complete. Reading each block's own Tags property suggests vanilla misses 13 craftable blocks, but BlocksFromXml.CreateProperties inherits properties through the Extends chain, so a block with no Tags of its own carries its parent's. shotgunTurret and m60Turret extend autoTurret; the industrial lights extend ceilingLight01_player; the garage door variant helpers extend their powered parents. Resolving Extends gives 6 of 6 trap recipes and 26 of 26 craftable electrician blocks already tagged. The 27th, carBattery, is an item and not a block at all.

- lbd_audit.py now resolves Extends itself, for Tags and for Harvest drop tags, which inherit the same way and are what RequirementBlockHasHarvestTags actually reads - it tests the block's drop entries, not its Tags. Inheritance applies only where the child does not define the property, param1 exclusions are honoured, and the chain is cycle guarded.
- On the back of that it checks every block requirement in the mod - RequirementIsTargetBlock, RequirementCraftedBlockHasTags, RequirementBlockHasHarvestTags and BlockHasName, the last with wildcard matching - against the resolved block list, and reports any that match no block. A requirement naming a tag nothing carries is dead in exactly the way an undefined cvar or an unresolvable buff name is, and those were the two bugs that cost the most to find this round. All ten distinct block requirements currently match: trapsSkill 7 blocks, electricianSkill 96, workstationSkill 8, treasureHunter 9, buriedTreasure 7, salvageHarvest 1446, oreWoodHarvest 151, and the Workstations block_name glob 3.
- Attribute first threshold dropped from 5000 to 1200 on all five, the same number every perk already uses. Three logged sessions put an attribute at roughly 10 XP a minute, which made 5000 an eight hour first level and about 209 hours to reach 10 - some seventeen times what maxing a five level perk costs, while attributes actually accrue faster than perks because each draws on seven to nine award paths rather than one or two. That inversion was the pacing bug. At 1200 the first level lands inside two hours and the full ten total 31,150 against a perk ladder's 7,442, so an attribute is still four times the commitment, through having twice the levels rather than through costing more per level. $lbd_xp_curve_multiplier stays at 1.2 - it is global, and moving it would have dragged every perk and crafting skill along with it.
- Movement XP is throttled to a 10s tick, matching the duration Healing Factor has always used. The old 1s was never even the constraint - the triggers arrive about 5s apart on their own - so the throttle was doing nothing and movement ran at whatever rate the player happened to move. 10s caps it near 6 XP a minute however hard you walk. Pack Mule keeps the 5s it was deliberately given, and Healing Factor its 10s.
- Where a progression's movement awards shared a cooldown with its combat, harvesting or crafting awards, they now have their own. attAgility, attFortitude and perkMediumArmor each gained a buffLBD_<name>_MoveCoolDown at 10s, and only their movement triggered effects were moved onto it - 10, 8 and 6 effects respectively - so everything deliberate keeps the 1s rate. perkFromTheShadows and perkRuleOneCardio are movement only, so their existing cooldown just went from 1s to 10s.

The onSelfWalk and onSelfCrouchWalk paths are gone, eight effects in all, and the group's movement gate dropped walking, crouching and slow swimming to match. onSelfRun and onSelfCrouchRun remain, and swimmingRun still counts.
- attAgility no longer pays for plain walking. It carried two onSelfWalk awards: one with no condition whatsoever, and one requiring you to be crouched with _lightlevel at or below 65. - Those three land together on attAgility - the threshold, the throttle and the lost walk award - and the sizing came from projection rather than measurement. If it now reads as starved rather than balanced, relax the 10s movement cooldown before touching the threshold again.
- Crafting skills have their own curve. - Spam crafting is now caught by identity rather than timing. A cooldown cannot throttle crafting at all: if an item takes longer to make than the cooldown lasts, every craft in a queue of twenty scores exactly as though it were twenty different items, and ten wooden clubs in a row really did hand over a level. Lengthening the cooldown only punishes slow, legitimate crafting by the same amount. Craft time is no help either - only 131 of 630 recipes set craft_time and not one of the T0 weapons or tools is among them.
- So each craft award now carries !CraftedItemMatchesCVar against a per skill $..._lbd_lastitem, with a recorder ordered last in the effect group so the comparison is against the PREVIOUS craft. Twenty identical items score once; twenty different ones score twenty times. Every one of the 23 crafting skills is wired, the paired Attempting debug lines carry the same requirement so the log cannot report XP that was not granted, and Crafting Seeds needed the trigger spelled onSelfCraftedRecipe rather than onSelfItemCrafted.

Version: 2.3.374.1712

- Crafting skills: restored the missing action cooldowns. Four were defined with a lowercase skill name while every reference used camelCase - buff names are case sensitive, so buffLBD_craftingSalvageTools_ActionCoolDown and the Shotguns, Sledgehammers and Spears equivalents resolved to nothing and their definitions sat orphaned.
